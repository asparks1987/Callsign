# Callsign Canonical Burndown

> **Canonical task source:** This file is the engineering plan of record. Generated HTML and `docs/reference/BURNDOWN.md` must link here rather than maintain separate task status.

## Purpose

This burndown turns the existing Callsign documentation and recorded Alpha status into a dependency-aware implementation plan. It distinguishes the current `v1.0 alpha` release from the complete `Alpha v1` family (`v1.0` through `v1.3`) and from later Beta work.

This documentation pack did **not** execute the repository build, install the application, use a real microphone, or verify a fresh-machine release. Statuses imported from the existing repository are therefore prefixed with **Documented**. They describe what the existing docs claim, not new independent proof.

## Release vocabulary

| Term | Meaning |
|---|---|
| `v1.0 alpha` | Current first-public-release target: install, profile, enrollment, service wake, callsign gate, overlay/readout, and visible Start-menu app launch. |
| `v1.1 alpha` | Visible dictation and explicit text handoff. |
| `v1.2 alpha` | Visible browser open/search/navigation with external-side-effect boundaries. |
| `v1.3 alpha` | Policy-gated Windows/WSL/Linux system control and Explorer-backed file search. |
| `Alpha v1` | The full `v1.0`–`v1.3` release family. |
| `Beta` | Supported packaging, signed artifacts, updates, migrations, platform matrix, privacy controls, and public release proof after Alpha is demonstrated. |

## Status and evidence rules

| Status | Meaning | Allowed evidence |
|---|---|---|
| `Documented done` | The pre-pack repository burndown claimed the work was done. It remains provisional until current evidence is attached. | Passing automated output plus source/commit reference, or a dated manual evidence record. |
| `Documented in progress` | The pre-pack documentation claimed partial implementation or incomplete proof. | Current implementation notes and partial test evidence. |
| `Not started` | No adequate implementation or proof was established from the reviewed docs. | None yet. |
| `Blocked` | An external decision or prerequisite prevents completion. | Named blocker, owner, and unblock condition. |
| `Deferred` | Explicitly excluded from the named release. | Canon or ADR naming the later release. |

A task may move to plain `Done` only when its acceptance criteria are met and its verification evidence is recorded against a commit or release artifact. Passing documentation checks alone never proves runtime behavior.

## Global release gates

1. **Canon gate:** root canon, product spec, release ladder, README, and public site make compatible claims.
2. **Safety gate:** wake, identity/session gate, policy, visibility, approval, stop, and audit rules cannot be bypassed.
3. **Evidence gate:** automated and manual proof names the commit, artifact hashes, machine/environment, commands, and actual results.
4. **Packaging gate:** a clean user can install, repair, start, stop, update, and uninstall without developer tooling.
5. **Privacy gate:** audio, voice samples, transcripts, UI observations, paths, logs, and telemetry follow documented defaults and retention.
6. **Fresh-machine gate:** release claims are demonstrated on supported clean Windows environments.
