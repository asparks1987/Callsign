Voice Access Parity Matrix

Definition

Callsign reaches practical Windows Voice Access parity when a user can control common Windows desktop work by voice with the same useful command families as stable Windows 11 Voice Access, while Callsign still requires:

Callsign -> identity verification -> command -> visible action

The parity baseline is stable Windows 11 Voice Access. Legacy Windows Speech Recognition macros and Copilot voice/vision actions are not part of the Free parity requirement.

All parity features are Free/MIT open-core features through Alpha v1.

Non-negotiable Callsign differences

  • Callsign wake comes from the audio wake detector, not transcript text alone.
  • The post-wake identity utterance is identity-only.
  • Commands run inside a short visible verified session.
  • Higher-risk commands can require approval or a fresh identity check.
  • Every command remains policy-gated and auditable.
  • The user must see listening, transcript/readout, pending command, action, and stop/cancel state.

Command execution pipeline

Every command family must use this pipeline:

speech transcript
-> normalized intent
-> command registry resolution
-> policy evaluation
-> approval or fresh identity if required
-> visible execution
-> verification
-> audit log

No command pack can bypass wake, identity, policy, visibility, or audit. Identity authorization is valid only while the state machine is actively waiting for a command, ready to launch, or visibly launching. Completed, cancelled, timed-out, and locked-out terminal states must clear verified identity and pending command/app data so stale authorization cannot be reused after the short verified session ends. Audit records include a correlation id plus a compact verification object so visible execution can be tied back to the command path that produced it. Built-in policy audit records mark policy_evaluation verification before allowed commands proceed. Built-in browser, dictation, extension-pack UI, file-search, help discovery, visible UI, voice control, update splash, and system execution records mark visible_status verification when the visible Browser, Dictation review/correction, Packs, Files, command palette/walkthrough, overlay/grid, voice-control status, update splash, or System status surface is updated. The background service also writes profile-scoped alpha.service_command_execution audit entries with audit_source set to service_runtime for service-executed browser, file-search, dictation, system, UI, extension, and Start-menu actions, so runtime snapshot history is backed by the same JSONL audit trail as visible UI commands. If the service cannot write that audit entry, the visible status and recent-action history include an Audit warning with bounded recovery guidance instead of suppressing the failure. Extension command audit uses one correlation id across registry resolution, policy or approval decisions, and pack execution, then records registry_resolution, policy_evaluation, user_approval, or pack_execution as the verification phase.

Extension pack requirements

Built-in Free parity commands should be implemented as normal command packs where practical.

Community packs:

  • import normal Windows .dll filenames through the Packs UI with Import Pack... or Import Folder..., or drag-and-drop one or more .dll files/folders into the full Packs tab or pack list,
  • automatically discover newly dropped .dll packs in the watched Packs folder so imported commands appear without a manual refresh,
  • show the visible import splash for newly discovered packs so their commands and features are announced before enablement, and preserve the most recent import splash summary so read import summary again can replay it after restart,
  • start disabled by default when imported through the UI,
  • must show command metadata, tier, signature status, entitlement status, and safety gates before enablement,
  • can be disabled and re-enabled,
  • must not bypass policy evaluation.

Future paid packs:

  • are entitlement-gated for pack loading and command routing,
  • are still policy-gated for execution,
  • receive identity and fresh-identity proof from the active session state machine at execution time,
  • must be signed, updateable, disableable, and rollback-capable.

Release acceptance

No release can claim 100% Voice Access parity until:

  • every parity category above is Done,
  • automated smoke coverage passes,
  • .\scripts\voice_access_parity_evidence.ps1 writes structured evidence for the matrix, installer, generated parity page, and named manual/live proof status; -WriteManualEvidenceTemplate prepares the release walkthrough evidence file, including the import-splash replay walkthrough,
  • a clean install walkthrough passes, exposes the Account, Voice, Session, Shortcuts, Plans, Updates, and Packs surfaces, and reaches the visible release-proof step before release,
  • the latest installer is built,
  • the public website serves the latest installer,
  • and the parity matrix is regenerated into the public docs site.
